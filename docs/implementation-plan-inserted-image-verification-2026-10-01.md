# 既存エビデンスシートへの画像追加失敗：調査結果と修正計画

対象ソース: `4bc627649c6aafbf18f800b26e44a8d0139d5f9f`、配布版 `0.1.0-preview.32`。
状態: 計画に沿った実装・テスト・配布生成が完了。配布版 `0.1.0-preview.33`。[改修検証記録](review-inserted-image-verification-2026-10-01.md)を参照。単体170件、実Excel11シナリオ、最終の影響2シナリオ再確認、200／500図形各10回の計測が合格した。ユーザーの元Workbookは未提供のため、元シート固有条件の確認は未実施。

## 報告と特定できた経路

既存のエビデンスシートへ画像を追加すると、次のメッセージが表示される。

> 自動配置に失敗したため変更を取り消しました: The inserted image Shape could not be verified.

`ExcelAutomaticPlacementService.PlaceImages` → `ExcelImagePlacementService.PlaceImage` → `PlaceWorkbook` の経路で、Excelの `Shapes.AddPicture` 自体は画像Shapeを返している。その後、Name設定、AlternativeText設定、LockAspectRatio設定、Placement設定を行い、以下のいずれかに該当すると画像を削除して失敗を返す。

- 名前が設定した管理名と一致しない。
- Topが「配置セルのTop＋縦オフセット」と0.05ptを超えて違う。
- WidthまたはHeightが計画サイズと0.05ptを超えて違う。

自動配置の呼び出し側はその失敗を受け、既に配置した画像と追加した行を戻して日本語のメッセージを付ける。末尾整理・fingerprint処理に到達する前の画像挿入後検証の失敗であり、処理時間の増加によるエラーと判断する証拠はない。

Top／Width／Heightの比較は、横並び補正のcommit `e199b4d`で追加された。直後のCOM高速化commit `23de30e`ではこの箇所を変更していない。名前の確認だけだった旧処理より、Excelが返すgeometryの違いを拒否する条件が増えている。

## 実Excelで確認したこと

ユーザーのWorkbookは操作せず、既存のテスト監督処理で生成・保存した一時Workbookと専用Excelプロセスを使用した。既存の製品サービスをそのまま呼び、別途、COMで直接挿入した画像の実値と比較した。ExcelはVersion 16.0、Build 19127。正常終了と生成Excelの終了を確認した。

| 条件 | 結果 | 意味 |
| --- | --- | --- |
| 通常の配置、非表示行をまたぐ配置、配置開始行が非表示、結合セル | 個別の直接COM試行は成功 | 非表示行・結合セルがあるだけで必ず失敗するとは言えない |
| 非表示行を含むシートで、製品サービスによるR4C4／R6C19への配置 | 成功 | 前回失敗したfixtureの説明だけから非表示行を原因と断定できない |
| 下方のR100000、縦オフセット3.06pt | Top予定値1,874,212.56pt、実値1,874,212.5pt。製品サービスで同じ英文エラー | 0.06ptの座標丸めでも固定0.05pt判定が拒否する |
| 上記でTopを予定値に再設定 | 実値は同じ。改善しない | 単純な再設定や無制限の再試行で丸めは解消しない |
| 全列非表示、製品サービスで画像挿入 | 同じ英文エラー | Excelが返す実Widthは0。実際に配置不能な状態も同じ文言になる |
| 全列非表示でWidth／Height／Left／Topを明示再設定 | Widthは0のまま | こちらは誤差許容の拡大で成功扱いにしてはいけない |

上記はエラーを発生させる機構の再現であり、ユーザーの既存シートがR100000や全列非表示だったと示すものではない。ユーザーの発生時の失敗項目・予定値・実値は、現行版では記録されていないため未確定。調査用の原記録と再実行用コードは `artifacts/placement-investigation` に保存した。

### 値の取得とテストに見つかった問題

`ExcelImagePlacementService.ReadDoubleProperty` は有限かつ正の値だけを採用し、それ以外を64へ置き換える。Left／Topの0は正常な座標だが、この処理では64へ変わる。Width／Heightが実際に0だった場合も64となり、検証時に本当の失敗値が見えない。配置座標とサイズの取得に同じ補正を使っている問題を修正対象とする。

前回の `RowMutationOptimizationChecks` は `SetRangeProperty(sheet, "10:10", "Hidden", true)` を使用していた。しかし共通補助処理 `SnapshotReadPerformanceChecks.SetRangeProperty` はHiddenの場合に常に `EntireColumn` を取得するため、この呼び出しは10行目ではなく全列を非表示にする。前回の同英文エラーの記録と、配置後に非表示を設定するfixture変更は、この誤った条件の影響を受けている。現在の追加検証も「10行目が非表示」の証拠としては使えない。

別の `SameSideBackfillChecks` は `EntireRow` を直接使用しており、こちらの非表示行条件とは区別する。前回のレビュー記録のfixture説明も訂正する。

## 修正方針と実装順序

### 1. 発生条件を確定できる診断と回帰条件を用意する

- 失敗メッセージを「位置を確認できない」「サイズを確認できない」「管理名を確認できない」に分け、日本語で予定値・実値・差を示す。既存の結果型とメッセージ経路を利用し、新しいログ基盤は作らない。
- エラー時に必要な診断情報をローカルへ記録する。配置セル、Side、予定／実Left・Top・Width・Height、処理段階、画像の論理サイズと倍率、Excel版、必要な非表示状態を対象とする。セル内容や画像内容はログに含めない。
- 現在の汎用64置換を診断には使わず、COMから読んだ実値を保存する。
- テスト補助処理の列非表示と行非表示を分ける。行は `EntireRow` を使用し、Hidden・Heightの実値をassertしてから画像を挿入する。全列非表示の試験も別条件として残す。
- ユーザーの元Workbookと同条件のコピーで診断結果を採る。未提供の間は一時fixtureで実装を進められるが、元の報告条件が解消したとの判定は保留する。

### 2. 共通の画像配置処理で値の扱いを修正する

- Left／Topは有限な0以上をそのまま取得する。Width／Heightは有限かつ正を要求する。取得不能・非数・負値・サイズ0を架空の64へ置き換えない。
- 挿入前に予定geometryと配置可能なSide幅を検証する。非表示によって配置幅がない場合は、画像や行を変更する前に理由を示す。ユーザーの行・列を自動で再表示しない。
- 挿入直後の実値と属性設定後の実値を再現試験で比較する。実サイズの変化を補正する必要が確認された場合だけ、作成したShapeへgeometryを1回再設定して読み直す。座標丸めだけの状態では再設定を繰り返さない。
- 比較は「計画値とExcelで表現可能な値の差」と「実際のNEW／OLDの差」を分ける。大座標の丸め許容量は実測と数値表現の精度を根拠に限定して設ける。一律に0.5pt／1ptへ拡大したり、geometry検証を削除したりしない。
- Sizeが0、CASE外、Side幅超過、別Shape、明確なサイズ不一致は失敗のまま扱う。サイズの絶対／相対誤差を無条件に増やさない。
- この変更はまず `ExcelImagePlacementService` に集約する。自動／手動配置と画像配置Redoの呼び出し元に同じ補正を重複追加しない。

### 3. 横並び・履歴・失敗時の取り消しを確認する

- `ExcelAutomaticPlacementService` の両Sideの実Top比較と、`ExcelManagedShapeService.TargetUnchanged`／`PairedImageResize` の参照画像・履歴検証を確認する。計画値の丸め対応を、外部編集検知の緩和へ波及させない。
- 横並びの基準は参照画像の実Topとする。実際のNEW／OLDのTop差0.05pt以内を維持する。表現可能な共通位置で満たせない場合は理由を示して安全に中止する。
- 履歴には実際に配置したgeometryを保存し、Undo／Redoで同じ位置を再現する。左端・上端0の画像も対象にする。
- 検証失敗時の作成Shape削除を確認する。現行の `TryDeleteShape` は削除エラーを握りつぶすため、削除失敗時に「変更を取り消しました」と断定しないよう、既存の結果・補償エラー経路へ結果を伝える。結果不明時に行削除の補償を続行しない。
- 原因が配置検証である以上、末尾整理の高速化・fingerprintの項目・native backupをこの修正のために変更しない。

### 4. 検証と配布

既存テストに次の境界を加える。COM模擬値だけで合格にせず、実Excelでgeometryを独立に読み取る。

- 既存の画像・セル内容があるシートへのNEW追記、NEW先行→OLD後追い、「同じSideの次CASE」を複数CASEで使用。
- 通常の座標、Left／Topが0、小数オフセット、下方の大座標、参照画像をセル内で動かした状態。
- 非表示行をまたぐ状態、開始行の非表示、非表示列の混在、全幅が非表示、結合セル。行／列の実際の非表示状態も検証する。
- 0幅／0高さ／明確なgeometry不一致は拒否し、既存画像・値・数式・書式を保持する。
- 挿入済み行と複数画像がある状態の途中失敗、Shape削除失敗、行変更結果不明では、残存変更と復旧情報を正しく通知する。
- Undo／Redo後の実Top、サイズ、参照画像の外部編集拒否。4CASE横並びシナリオと行変更の安全性試験も再実行する。

Release build警告0、単体テスト、影響する実Excelシナリオを確認する。通常成功経路に全Shape走査を追加しない。追加COM取得は配置対象Shape中心に限定し、既存の200／500図形条件で配置時間に継続的な悪化がないか確認する。合格後に配布版を更新し、単一EXEとSHA-256を生成する。

## 完了条件

1. ユーザーの報告条件に相当するコピー／fixtureで、失敗した具体的な項目と値を確認でき、正常な追記が成功する。
2. 実際のNEW／OLDの横並び、CASE境界、履歴の外部編集検知を維持する。
3. 配置不能・削除失敗を成功扱いにせず、取り消し後の状態と復旧情報が正しく表示される。
4. 非表示行fixtureの誤りを修正し、前回の検証記録を訂正する。
5. 影響範囲のテストと配布生成が合格し、確認できていないユーザー条件は明記する。

計画の中心は、追加された検証を外すことではなく、実値の取得・丸めと配置不能の区別・誤ったテスト条件を直すこと。ユーザーのシートでの具体的な失敗値が分かり次第、その項目に修正範囲を絞る。
